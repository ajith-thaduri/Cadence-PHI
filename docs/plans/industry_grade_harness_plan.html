1. Executive summary

Current state. The detection engine is already production-shaped: - typed contracts; - coordinates always in the original text; - a full evidence chain for every decision; - Presidio orchestration with its silent filtering bypassed; - detection and redaction kept separate; - calibration that only uses development data; - a tool for manual evaluation.

The gap. The assurance layer around the engine is still research-grade: - the repository is not under version control; - failure handling is undefined and untested; - there are no release gates and no confidence intervals; - the gold data is fabricated and single-annotated; - the token vault is in-memory and unencrypted; - entity behaviour is partly hard-coded in Python; - there is no performance testing and no monitoring.

What industry practice requires. NIST AI RMF, NIST SP 800-188 and 800-53, 45 CFR 164.514, the vendor transparency documents and the de-identification literature agree on the following: - Recall is the release metric. Gate on its lower confidence bound for each entity and modality, not on F1. - Release evidence must come from real data in deployment conditions. - The system must fail closed, and this must be proven by fault injection. - Every output is stamped with the config hash, model hash and code commit. - Configuration separates policy from mechanism. It is strictly validated, composed from layers and hashed. - The re-identification map is randomly derived and strongly protected. - Behavioural (CheckList) suites and a regression baseline run on every change.

Plan in brief. Six phases:

Phase Content
P0 Foundations version control, fail-closed behaviour, PHI-free logging
P1 Configuration and entity catalog entity behaviour moves out of code
P2 Evaluation core three-view metrics with confidence intervals, contamination control, redaction checks, stage attribution

2. Industry research findings

2.1 Assurance frameworks (TEVV)

NIST AI RMF 1.0, MEASURE function [V]. Testing, evaluation, verification and validation (TEVV) must be documented and repeatable: - MEASURE 2.1: test sets, metrics and tools are documented. - MEASURE 2.3: evaluation happens under conditions representative of deployment. - MEASURE 2.6: the system fails safely. - MEASURE 1.3: there are independent assessors. - Privacy risk is examined explicitly.

Good Machine Learning Practice (FDA, Health Canada, MHRA; IMDRF N88 2025) [S]: - test data stays independent of training data; - reference standards are fit for purpose; - the system is evaluated in clinically relevant conditions; - deployed performance is monitored.

CHAI Applied Model Card (draft v0.1, 2024) [V]: - a release-level card covering safety/reliability, fairness and usefulness; - the card is re-issued on any change of use, risk, metric or structure.

Regulatory status notes: - ONC HTI-1 model-card requirements are proposed for removal under HTI-5 [S], so they should not be cited as binding. - SR 11-7 model risk management is useful as an analogy only (independent validation, ongoing monitoring). It was reportedly rescinded in 2026 [S].

2.2 De-identification standards

  • 45 CFR 164.514(b) Safe Harbor [V]:
    • removes the 18 identifier types, including all date elements except the year, ages over 89, geography below state, and the first three ZIP digits under the population rule;
    • Expert Determination requires a "very small" re-identification risk, with no numeric threshold.
  • 45 CFR 164.514(c) [V]: a re-identification code must not be derived from or related to information about the individual, and the mechanism must not be disclosed.
  • NIST SP 800-188 (2023) [V]:
    • de-identification software must be verified for correctness, containment (no leaks "in expected or unexpected ways"), usability, efficiency, scalability, repeatability and transparency;
    • lookup-table pseudonyms "must be randomly assigned", and the table must be highly protected;
    • tests should use conspicuously non-natural fakes such as "FIRSTNAME1".
  • HITRUST de-identification framework [S]: the organisation must define its own thresholds and governance.
  • NIST SP 800-38G Rev.1 (FF1 format-preserving encryption, 2nd draft, 2025) [V]: FF3 is removed and the minimum domain is 10⁶. Ages and day-of-month fields are therefore not FF1 domains.

2.3 How production de-identification services are built and documented

  • Google Sensitive Data Protection / Healthcare API [V]:
    • inspection config (infoTypes, custom detectors, exclusion and hotword rules, likelihood) is separated from de-identification config (transformations);
    • reusable templates;
    • a version field on infoTypes, though templates themselves are not versioned. That is a gap we should not copy.
  • AWS Comprehend Medical DetectPHI [V]: returns ModelVersion and a confidence score on every response.
  • AWS Transcribe PII redaction [V]: "does not meet the requirements for de-identification under HIPAA".
  • Azure Health Data Services de-identification [V]:
    • its primary release criterion is recall, with a goal above 95% (entity-level, fuzzy matching);
    • it warns that "small datasets, synthetic data, and tests that don't reflect your end-to-end scenario are unlikely to sufficiently represent your production performance";
    • it prefers surrogates, but warns that consistent surrogation over large batches degrades privacy;
    • it is not recommended for real-time transcription.
  • presidio-research [V]: span (IoU) and token evaluators, F2, and a hierarchy-aware entity mapper. Suitable as an independent cross-check of our scorer.
  • Presidio itself [V, source]:
    • AnalyzerEngine.analyze() drops results below threshold, then drops results contained in a same-type result, so evidence is lost;
    • AnalyzerEngineProvider silently falls back to defaults when the config file is missing;
    • log_decision_process=True writes raw entity text to a logger.

2.4 De-identification literature

Architecture size: - One model plus rules plus dictionaries is the proven size: the i2b2 2014 winner (Yang & Garibaldi 2015) [S] and Dehghan 2015 [V]. - Ensembles add 1.1–1.5 F1 and no recall (Kim, Heider & Meystre 2020) [V]. - Rules plus dictionaries can reach 99%+ recall at roughly 78% precision (Philter, Norgeot 2020) [V]. - A hybrid beats the same NER model alone by about 10% (Kocaman 2023) [V].

Patient-specific dictionaries work: CRIS reached P 98.8 / R 97.6 (Fernandes 2013) [V]. Propagating confident detections to every mention also helps (Dehghan 2015).

Generalisation: - Expect 10–20 points lower at a new site: Yang 2019 fell from 0.955 to 0.857 F1 [V]. - Local fine-tuning plateaus at about 700 notes (Yang 2020) [V]. - Synthetic PHI overstates performance (Yeniterzi 2010) [S].

Speech (ASR): word error rate on PHI words was 41.8%, and recall of an i2b2-trained model on conversational transcripts was 0.37. Of the false negatives, 45% were caused by ASR and 50% by NER (Cohn 2019) [V].

Residual risk: - Every method leaves residual identifiers. - Realistic surrogates hid about 90% of leaked identifiers (Carrell 2013) [V], and motivated attackers found only 26.8% of leaked PII (Carrell 2020) [V]. - Consistent replacement turns tiny token miss rates into large document-level leakage (Osborne 2025) [V]. - Presidio uncustomised on clinical notes scored only P 0.51 / R 0.74 (Alrazihi 2025) [S].

2.5 Evaluation methodology

i2b2/n2c2 2014 [V]: - strict and relaxed entity matching; - binary token-level PHI recall; - HIPAA-only and full label sets reported separately; - double annotation plus adjudication, with inter-annotator agreement of token F1 0.93 and entity F1 0.895.

Small-sample statistics: - Rule of three (Hanley 1983) [S]: zero misses in n gives a 95% upper bound of about 3/n on the miss rate. About 300 mentions per category are needed to bound the miss rate below 1%. - Use a cluster bootstrap over documents (tokens within a document are correlated). - Use Wilson or Clopper-Pearson intervals for proportions. - Use paired approximate randomisation to compare system versions (Dror 2018) [S].

Behavioural testing with CheckList (Ribeiro 2020) [V]: - minimum functionality tests (MFT); - invariance tests (INV); - directional tests (DIR).

They find failures that held-out accuracy misses.

Documentation: model cards (Mitchell 2019) and datasheets (Gebru 2021) [S].

2.6 MLOps, reliability and security

  • ML Test Score (Breck 2017) [V abstract]:
    • check the model before serving (startup self-test on canary data);
    • monitor the deployed model;
    • make readiness the minimum across test areas.

  • Fail-safe controls in NIST SP 800-53 [V]:

    • SC-24: fail in a known state;
    • SI-17: fail-safe procedures;
    • SI-11: error messages carry no sensitive information.

    No vendor documents "fail-closed redaction" explicitly, so these generic controls are the basis. - Latency targets are set as p50/p95/p99, not means. Load, soak and cold-start testing are standard (Google SRE) [S]. - Document size limits: Azure accepts 50 KB per request and AWS 20 KB per call [V]. Inputs beyond the limit must be rejected or split, never silently truncated. - HIPAA technical safeguards (45 CFR 164.312) [V]: access control, audit controls, integrity, transmission security. - Logs may hold only keyed hashes. Plain hashes of a DOB or SSN can be brute-forced. - Production leak monitoring is emerging practice, not standardised. It covers detection-rate control charts, sentinel canary records sent through the real path, an outbound payload scan, and sampled human review.

2.7 Unsettled in industry, to be raised with stakeholders

  • What numeric recall thresholds to adopt.
  • How to calibrate de-identification confidence scores.
  • How to monitor leaks in production.
  • The right scope for consistent tokens.
  • Whether a PHI-minimised payload sent to a BAA-covered LLM needs Expert Determination. It is generally not legally "de-identified". This is a legal question.

Principles

  1. Policy is separate from mechanism.
    • Entity behaviour (enablement, risk tier, thresholds, actions) lives in configuration.
    • Recognizers only declare which entities they can emit.
  2. Runtime and evaluation are separate packages.
    • Gold labels, gate thresholds and datasets never reach the engine.
    • An import rule enforces this.
  3. Fail closed by default, proven by fault injection.
  4. Every artifact is versioned and stamped. Every response and report carries the config hash, model weight hash, code commit and catalog version.
  5. Gate on recall lower bounds per risk tier and modality. Also gate on document-level sanitisation, regression, behavioural, security and performance results. Any single failure means no-go.
  6. Detection and redaction are judged independently. Residual PHI is measured on the output.

6. Configuration architecture

6.1 Recommendation

Split configuration by owner and change cadence, then compose it into one resolved, strictly validated, hashed artifact. Evaluation configuration stays out of the runtime.

This follows four precedents: - Google DLP's inspect/de-identify split; - Hydra-style ordered composition; - Kustomize-style base-plus-overlay environments; - Presidio's own pydantic validation, without its silent default fallback.

Why not one file: - every change becomes a mixed-ownership diff (privacy policy vs detector mechanics); - environment differences can't be restricted; - evaluation settings leak into production.

Why not many unconnected files: behaviour becomes unauditable unless the files compose into one hashed artifact.

6.3 Example: entity catalog (entities.yaml)

catalog_version: "2026.10.0"
risk_tiers: {direct: "uniquely identifies a person", quasi: "identifies in combination", contextual: "organisational context"}
entities:
  NAME:
    description: "Name of the member (patient) or other individual referred to as the subject"
    category: person
    hipaa_safe_harbor: [names]
    risk_tier: direct
    enabled: true
    default_action: TOKENIZE
    aliases: [PERSON, PATIENT_NAME]
    subtypes: [MEMBER_NAME, PARTIAL_NAME, SPELLED_NAME]
    core_chars: {strip_titles: [dr, mr, mrs, ms, miss, sr, sra, nurse], strip_edge_words: true}
    outbound_guard: block
  PHONE:
    description: "Telephone or fax number"
    category: contact
    hipaa_safe_harbor: [telephone, fax]
    risk_tier: direct
    enabled: true
    default_action: TOKENIZE
    subtypes: [PHONE, FAX, PARTIAL_PHONE]
    outbound_guard: block
  DATE:
    description: "Any date element (except year) related to an individual"
    category: date
    hipaa_safe_harbor: [dates]
    risk_tier: quasi
    enabled: true
    default_action: TOKENIZE          # alternative: GENERALIZE (keep year)
    subtypes: [ADMISSION_DATE, DISCHARGE_DATE, APPOINTMENT_DATE, PROCEDURE_DATE, SERVICE_DATE, RELATIVE_DATE]
    core_chars: {strip_edge_words: true}
  AGE_OVER_89:
    description: "Age above 89 and its elements (Safe Harbor)"
    category: person
    hipaa_safe_harbor: [age_over_89]
    risk_tier: quasi
    enabled: false                    # opt-in until its recognizer is developed and evaluated on dev data

Every other file refers to entities by catalog id, and the schema rejects unknown ids. The engine reads risk tier, actions, core-character rules and outbound-guard behaviour from the catalog. These replace the Python constants HIGH_RISK, DEFAULT_TITLES, ID_AFFIXES and EDGE_WORDS.

6.4 Example: declarative pattern recognizer (recognizers/patterns.yaml)

patterns:
  rule_npi:
    version: "1"
    entity: NPI
    patterns:
      - {name: npi_keyword, regex: '(?i)\bNPI\b\W{0,3}(\d{10})\b', group: 1, score: 1.0}
    validators: [npi_luhn]            # named validator → score_type checksum_valid
    context: [npi, provider]
    developed_on: [synthetic_dev]
  rule_ssn:
    version: "1"
    entity: SSN
    patterns:
      - {name: ssn_dashed, regex: '\b(?!000|666|9\d\d)\d{3}-(?!00)\d{2}-(?!0000)\d{4}\b', score: 0.9}
    context: [ssn, social security]
    enabled: false

Adding a deterministic entity needs no code: 1. add a catalog entry; 2. add a pattern entry; 3. optionally add policy overrides.

A test proves this. Complex families (spoken-number parsing, conversational rules) stay in code, but take every keyword, guard and score from contextual.yaml.

6.6 Resolution order and hashing

  1. Composition root and its includes, in a fixed order.
  2. Environment overlay. Only allow-listed keys may change. Prod cannot lower thresholds, disable a direct-identifier entity or turn off the outbound guard.
  3. Generated calibrated overlay, validated against provenance.
  4. CLI overrides (evaluation only).
  5. Request allow-lists, which can only narrow what is enabled.

Then strict Pydantic validation: - extra="forbid"; - value ranges checked; - references checked against the catalog; - the loader refuses to start if a file is missing.

The validated config is serialised to canonical JSON and hashed with SHA-256. Every response and report is stamped with: - config_sha256 - catalog_version - code_commit - model_weight_sha256 - engine_version

python -m harness.phi.config validate --env prod prints the resolved hash.

6.7 Threshold precedence (current order kept, plus modality)

For model_confidence evidence, the most specific setting wins:

model×entity×modality > model×entity > entity×modality > entity > model > recognizer > default

Deterministic and registry evidence keeps its own semantics: recognizer > deterministic_default. Entity and model ML thresholds never suppress deterministic or registry evidence.

6.8 Migration

  • configs/phi_harness.yaml stays readable.
  • python -m harness.phi.config migrate splits it into the new layout.
  • An equivalence test asserts that old and new layouts produce identical detections on the regression corpus.

7.2 Entity policy

  • Per entity:
    • action (TOKENIZE / REDACT / SURROGATE / GENERALIZE_YEAR for dates);
    • per-modality thresholds;
    • consistency scope;
    • outbound-guard behaviour (block for every direct identifier).
  • New entities start enabled: false. They are enabled only after their recognizer is developed on dev data and passes the behavioural suite. Each change is logged in the rule changelog.
  • Evaluation subtypes carry the fine-grained requirements (spouse, admission date, hospital …) without growing the runtime taxonomy. Reports cover every canonical entity and every subtype.
  • The generated responsibility matrix flags:
    • entities with no enabled recognizer;
    • entities with a single point of failure;
    • mismatches between expected and actual source in evaluation.

8. Recognizer and model strategy

  • Deterministic rules.
    • Simple families move to declarative patterns.yaml.
    • Validators are chosen by name (luhn, npi_luhn, date_valid).
    • Complex parsers (spoken numbers) stay in code, with their parameters in configuration.
  • Conversational / ASR rules stay in code.
    • Keywords, guards and scores move to contextual.yaml.
    • Each rule is developed on dev data only and logged in docs/rule_changelog.md.
  • Registry.
    • Matching parameters move to registry.yaml.
    • Access stays scoped to the subject plus versioned directories.
    • Each lookup is audited by subject id and directory version, never content.
    • Each match records match_type, registry_type and registry_version.
  • One production model: OBI RoBERTa, behind the generic ModelRecognizerAdapter.
    • The weight SHA-256 is verified at load; a mismatch fails closed.
    • Revision and hash are stamped on every response.
    • mode: production | shadow | disabled. Shadow evidence is recorded and evaluated but never changes a decision, so a future model can be trialled without risk.
    • Stanford V2 and MedNotes GLiNER remain experimental adapters.
  • Recognizer contract tests that every recognizer must pass:
    • never mutates text;
    • spans stay within bounds;
    • emits declared entities only;
    • deterministic;
    • within its time budget on the long-document fixture.

  • Model-change protocol:

    1. shadow run;
    2. paired approximate-randomisation comparison on the release set;
    3. all gates;
    4. system card re-issued.

    A second production model requires the pre-registered materiality protocol. The literature shows ensembles add no recall (§2.4).

9.2 Metrics

Every metric is defined in configs/eval/metrics.yaml and computed from the same predictions.

Core definitions

Term Definition
Core characters Alphanumeric characters of a gold span, excluding titles, ID affixes and edge function words, as defined in the catalog.
Entity TP A gold entity overlapped by a REDACT/REVIEW detection. Full if every core character is covered.
Entity FN Otherwise.
FP A detection overlapping no gold entity and no ignore region.

Three scoring views

  1. Leak view: binary character-level and token-level PHI recall. Residual PHI characters (and %) are measured on the redacted output (§12).
  2. Entity view:
    • strict (exact span) and relaxed (any overlap / full core) recall;
    • precision and F2 per entity, subtype and risk tier.
  3. Document view:
    • fully-sanitised document rate (no direct-identifier leak);
    • "all mentions masked" rate per entity instance.

Utility metrics: - over-redaction (non-PHI characters redacted); - spurious spans per 1,000 characters; - the false-positive rate on negative prompts; - must_not_redact violations.

Per-recognizer metrics (§11.2): - contributed; - sole catch; - false positives contributed; - marginal loss when ablated; - precision of accepted evidence.

Statistics: - document-level cluster bootstrap, at least 1,000 replicates, percentile 95% CI; - Wilson intervals for proportions; - the rule of three for zero-miss categories; - a paired approximate-randomisation test when comparing versions; - support below the gate minimum is reported as "insufficient evidence".

Strata: entity, subtype, risk tier, modality (typed / note / dictation / telephone / ASR), document type, length bucket and chunk count. Name origin is added when the data allows (fairness).

Cross-check: presidio-research span and token evaluators on the same predictions. Any difference must be explained by documented definitional differences.

9.3 Gold and test-data management

  • Dataset manifests (configs/eval/datasets.yaml) record for each dataset:

    • id, path and SHA-256;
    • role (dev, test, holdout, suite, release, regression);
    • provenance;
    • PHI class (fabricated, public, real_governed);
    • access class, licence and retention date.

    Calibration and rule development read the role, never the dataset name. - Annotation guidelines (docs/annotation_guidelines.md, versioned) define: - entity boundaries (titles, affixes, edge words); - subtype rules; - ignore regions; - how to annotate ASR loss. - Release sets are double-annotated and adjudicated, with agreement reported as pairwise F1 on tokens and entities. - Gold files carry a schema version. Every gold change is logged with its reason. Annotation errors are the only valid reason; changing gold "to match the system" is never allowed. - Contamination prevention: - exact and near-duplicate detection (shingled Jaccard or MinHash) between dev and test/holdout/suite/release, and between prompt-suite items and dev. CI fails above a threshold; - the evaluation ledger (below) records every frozen-test access. - Evaluation ledger: results/ledger.jsonl, append-only. Each run records: - run id and timestamp; - config hash, code commit and model hash; - dataset ids and hashes; - headline metrics; - operator. - Datasheet per dataset: provenance, consent or BAA basis, annotation process, agreement, known gaps, retention.

10. Prompt suite and test-case design

10.1 Format

The suite lives in eval_suites/english_v1/prompts.jsonl, one prompt per line. Spans are anchored by text, so no offsets are typed by hand.

{"prompt_id": "C-007", "group": "C_conversational", "modality": "telephone", "holdout": false,
 "text": "Her birthday is April twelve nineteen eighty-five and her number is four one five five five five zero one nine eight.",
 "registry": null,
 "expected": [
   {"entity_type": "DOB", "subtype": "SPOKEN_DOB", "match": "April twelve nineteen eighty-five", "occurrence": 1,
    "expected_action": "REDACT", "expected_sources": ["DETERMINISTIC", "CONVERSATIONAL"]},
   {"entity_type": "PHONE", "subtype": "SPOKEN_PHONE", "match": "four one five five five five zero one nine eight",
    "expected_action": "REDACT"}],
 "must_not_redact": ["birthday"],
 "asr": null,
 "status": "expected_pass", "notes": ""}

How the format works: - The loader resolves match and occurrence to [start, end). It fails on zero or ambiguous matches, and freezes the result as prompts.resolved.jsonl with a hash. - must_not_redact lists non-PHI anchors that must stay untouched. - asr (ASR prompts only) records the clean source and the PHI the ASR destroyed: {"source_text": "...", "lost": [{"entity_type": "MEMBER_ID", "source_match": "..."}]}. This drives the ASR_destroyed outcome. - status is one of expected_pass, known_failure (with a reason) or exploratory. - holdout: true marks about 25% of prompts. These are excluded from debugging views and reported separately.

10.2 Groups

The groups follow the requested priority order. About 200 fabricated prompts in v1.

Group ~Count Content
A single-entity 50 each entity and subtype in each written form (e.g. PHONE with dashes, dots, spaces, parentheses, no separators, +1), one entity per prompt
B multi-entity clinical 25 notes and summaries with 3–8 entities; adjacent entities; punctuation boundaries; repeated PHI
C conversational 25 spoken DOB / phone / ZIP / email / addresses; ordinal dates; read-backs; self-corrections
D ASR-style 25 lowercase, no punctuation, fillers, "slash", split digits, misheard tokens; with asr.source_text and lost where structure is destroyed
E contextual 20 providers, relatives (spouse / parent / child / caregiver), employers and facilities not in any registry; targets OBI
F registry-scoped 20 scoped fabricated registry (member, spouse, member ID, DOB, phone); decoy prompts naming a different member's registered values, which must not produce registry evidence
G edge cases 25 initials; hyphenated and apostrophe names; similar names; multi-format dates; long addresses; PO boxes; mixed letter-digit IDs; PHI across sentence boundaries; PHI next to punctuation; PHI repeated many times
N negative / non-PHI 25 doses, vitals, counts, durations, drug names, eponyms, years alone, habitual weekdays, organisation name, generic roles; expected PHI is empty

Integrity rules: - Expectations are written before the engine is run. - After a run, an expectation may change only to fix an annotation error. The change is logged in eval_suites/english_v1/CHANGELOG.md. - The suite is never used to tune thresholds or develop rules. Fixes are developed on dev data (§13).

10.3 Expected vs actual record

Per expected entity, an EntityEvaluation record holds: - prompt id, entity type and subtype, expected span and text, expected action; - detection_status: detected_full, detected_partial or not_detected; - redaction_status: redacted_ok, redaction_failure or n/a; - post-redaction residual characters; - failure_reason and failed_stage (§11); - the responsible evidence: recognizers and source groups, raw scores, score types, thresholds with their source, final decision and reason; - expected sources vs actual sources.

Unexpected detections become FP records with recognizer, group, score, reason and any must_not_redact hit.

Per prompt, a PromptRecord lists the input, expected, detected, redacted, missed and unexpected entities, with the responsible recognizer and model, raw scores, thresholds, final decisions and failure reasons.

11. Failure-analysis strategy

11.1 Stage decision tree

Every gold entity receives exactly one outcome and one failed stage. The checks run in this order.

# Outcome Condition Failed stage
1 ASR_destroyed listed in asr.lost; no span exists in the transcript ASR
2 disabled_only only evidence comes from recognizers, models or normalizers disabled in this configuration configuration
3 policy_rejected evidence at or above threshold, but entity disabled, allow-listed, or REVIEW not redacted by policy policy
4 normalization_failure the only evidence comes from a derived view and was rejected for unsafe mapping, or was projected to a span not overlapping the entity normalization
5 below_threshold live evidence exists but all of it is below threshold (best rejected recognizer, raw score, threshold and source reported) threshold
6 no_candidate no evidence overlaps the entity recognition
7 reconciliation_failure accepted evidence fully covers the core, but no final detection does reconciliation
8 partial_span detections cover only part of the core characters (sub-cause: model boundary, rule boundary or word expansion) recognition boundary
9 redaction_failure detections fully cover the entity, but the redacted output still exposes core characters (§12) redaction
10 success detected in full and redacted correctly –

Required changes: - Outcomes 4 and 9 are new. - For outcome 4, evidence metadata must keep the derived-view span and a mapping-validity flag. - Known limitation: a normaliser that should have fired but didn't looks like no_candidate. The local report therefore shows the derived text view for each prompt to make this diagnosable.

11.2 Source attribution

Source groups are derived from configuration:

Group Recognizers
DETERMINISTIC rule_* and pattern recognizers
CONVERSATIONAL conv_*
REGISTRY registry_*
MODEL:<key> e.g. MODEL:obi_roberta
PRESIDIO presidio_*

Each accepted evidence item also records its view: original, or normalised with the normaliser ids.

Per entity and per FP, the evaluator records: - the contributing groups; - sole catch: only one group caught it, so it would leak without that group; - the group whose evidence set the final type; - expected vs actual source, checked against the catalog's responsibility matrix.

Marginal ablation: the suite is re-scored with each group disabled, reusing the collected evidence, so it is cheap. The result shows which entities each group uniquely protects and which false positives it adds, per entity type.

11.3 Triage workflow

Each miss is classified as one of: - a system error; - an annotation error (which goes to the gold changelog); - out of scope.

For system errors: 1. Write a similar but different fabricated example into the dev set. 2. Develop the fix there and log it in docs/rule_changelog.md. 3. Add the original case to the prompt suite as known_failure, flipping it to expected_pass once it is fixed on independent evidence.

11.4 Explainability

The report shows for every entity: - the text views; - every candidate (recognizer, raw score, score type, threshold and its source, accepted or rejected with reason); - the decision reason; - the confidence class.

In production: traces carry ids, counts and timings only. They never contain text.

12. Redaction and residual-PHI evaluation

  1. Detection status comes from the DetectionResponse alone.
  2. Redaction validation comes independently from the RedactionResponse:
    • every core character lies inside a Replacement original range;
    • the output at output_start–output_end equals the replacement token and contains no core character;
    • a vault round trip restores the original exactly;
    • tokens are not derived from PHI (format and randomness check);
    • consistency scope behaves as configured.
  3. Post-redaction re-scan of the sanitised text:
    • verbatim search for every gold surface;
    • normalised search (digits only for phones and IDs; case- and space-folded for names and emails) to catch leaks through a different mention;
    • the outbound-guard scan (the same component as production: rules plus registry);
    • an optional second engine pass, reported for information only;
    • the must_not_redact anchors must still be present.
  4. Residual and over-redaction metrics:
    • expected, redacted and residual PHI characters (and %) per entity, document, risk tier and modality;
    • verbatim leaks;
    • over-redacted characters;
    • must_not_redact violations;
    • fully-sanitised documents with CI.
  5. Fault test: an injected faulty operator must be reported as redaction_failure.
  6. Utility, later: the downstream task delta on sanitised vs original text.

13. Regression strategy

Baselines are recorded per release and stored as versioned JSON stamped with the config hash: - per-entity outcomes on T1 and T2; - per-prompt FP counts; - T3 headline metrics with CIs; - T7 percentiles.

Regression rules: - zero new misses in direct-identifier entities (G4) unless individually signed off; - no new redaction of negative or must_not_redact anchors; - no residual increase beyond the CI; - improvements on known_failure are reported, and the baseline is updated only by explicit command after review.

CI tiers:

Tier Contents Runs
Fast T0, T1 and T2 with rules and registry only, T5, T6 (no model weights) every change
Model T1 and T2 with OBI, T3 nightly
Release T4, T7, gate runner per release candidate

Re-validation triggers are enforced by the gate runner by comparing stamped hashes: - any config hash change; - a model, tokenizer, Presidio or transformers version change; - an ASR engine or ASR version change; - a new document type or line of business; - a drift alarm; - a confirmed leak; - at least once a year.

Failures become permanent regression cases. Every confirmed production or manual-evaluation miss becomes a fabricated known_failure prompt plus a dev example, and stays in the suite for good.

18. Testing and validation plan

  1. Unit and contract (T0):
    • schema rejections (unknown keys or ids, out-of-range values, forbidden prod overrides);
    • catalog-driven behaviour, including a test that adds a fabricated pattern entity in a temporary config with no code change;
    • metric fixtures with hand-computed CIs;
    • each stage-tree outcome built from constructed evidence;
    • an injected faulty operator detected as redaction_failure;
    • vault encryption, scope and audit;
    • log-filter rejection.
  2. Integration:
    • old and new config layouts are equivalent on the regression corpus;
    • engine plus outbound guard blocks an injected leak;
    • the runtime cannot import harness_eval (an import-linter rule);
    • registry scoping with decoy subjects.
  3. End to end:
    • the full CLI path (analyze → suite → gates) on fabricated data produces every report and a go/no-go document labelled "engineering evidence";
    • batch vs single-document consistency;
    • determinism across runs, plus a CPU vs MPS comparison.
  4. Behavioural (T1) and prompt suite (T2): versioned and baselined, with fast tiers in CI.
  5. Fault injection (T5): for every scenario, no LLM call and no pass-through. The response carries a fail-closed status and no PHI.
  6. Security (T6):
    • sentinel PHI is absent from logs, masked outputs and caches;
    • sockets are blocked;
    • a missing key fails closed;
    • the vault is unreadable without its key.
  7. Performance (T7): latency percentiles by stage and length bucket, 2× peak load, one-hour soak and cold start, each stored as a baseline.
  8. Synthetic smoke test: the end-to-end example plus the fast tier of the prompt suite.
  9. Release validation (T4): on governed real data only, under the gate runner, with independent review. Nothing before T4 is presented as release evidence.

All existing tests (132 today) must keep passing at every phase.
